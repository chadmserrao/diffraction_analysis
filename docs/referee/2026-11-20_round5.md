**2. [wrong result] `snapRing`'s "no ring peak near the click" branch is effectively unreachable inside the data, so a click in a featureless region snaps silently to a noise bump up to max(8 px, 5 % r) away**

Where: `/Users/cmserrao/Documents/GitHub/diffraction_analysis/src/imageproc.js:850-867`, used by `/Users/cmserrao/Documents/GitHub/diffraction_analysis/src/app.js:752-759`.

Input: any pattern; "+ Ring"; click at a radius with no ring, e.g. `r0 = 600 px` on a pattern whose rings sit at 400 and 900 px (`rMin < 600 < rMax`).

Happens: `win = Math.max(8, 0.05 * 600) = 30` px. The residual stored in `profile[i][3]` is `resid[b] = medS[b] - bg[b]` where `bg` is the **lower** convex hull of the log profile (`imageproc.js:648-660`), so `resid >= 0` everywhere with a non-zero noise level — `imageproc.js:662-663` estimates exactly that noise (`pn`) from `|resid[b] - mean(neighbours)|`. After the 1-2-3-2-1 smoothing (`:854`) the sequence is still non-monotone, so a 61-bin window (step = 1 original px when `f = 1`, i.e. any image ≤ 2048 px — `:284`, `maxWork: 2048`) contains several local maxima with `rs[i] > 0`.

Then note `:863-865`: the 0.25 × `hMax` gate can never empty the candidate set, because the strongest peak always satisfies `p.h >= 0.25 * hMax`. So **`peaks.length > 0` ⟹ `best !== null` ⟹ `snapped: true`**. The nearest noise bump wins, the ring is moved up to 30 px (5 % in r, hence ~5 % in d), `snap.snapped` is true, and `app.js:755` never fires the toast. Unlike the detected rings, this peak passed none of the detection's acceptance tests — no prominence check (`imageproc.js:676`), no `annulusStats` coverage/cv check (`:751-760`), no `rClear` beam-stop exclusion (`:750`).

Should: `snapped` should be false when the nearest peak is not a feature the detector would accept — e.g. require the same prominence floor (`max(4*pn, …)`) or an absolute offset limit — so the user gets the "ring placed where you clicked" message instead of a 5 %-wrong d-spacing. PROMPT §6 check 5 requires d within 2 %; this silently exceeds it.

Evidence: `imageproc.js:858` admits a peak on any `rs[i] > 0` local maximum; `:863-865` as written cannot return `null` once `peaks` is non-empty; `imageproc.js:648-663` shows `resid` is non-negative and noisy.

**3. [misleading claim] The new "Contrast" tooltip states the wrong direction**

Where: `/Users/cmserrao/Documents/GitHub/diffraction_analysis/src/index.html:63`

```html
<input type="range" id="rngGamma" min="0.3" max="2.5" step="0.05" value="1" title="Display gamma: slide left to lift faint features">
```

Input: drag the Contrast slider left, to `g = 0.3`.

Happens: `app.js:301-303` builds the LUT as `L[i] = 255 * pow(min(1, i/wl), 1/g)`. With `g = 0.3` the exponent is `3.33`: a pixel at 10 % of white maps to `255 * 0.1^3.33 ≈ 0.1` — faint features are **crushed to black**. With `g = 2.5` the exponent is `0.4` and the same pixel maps to `255 * 0.1^0.4 ≈ 101` — faint features are lifted. Sliding left does the opposite of what the tooltip says. (No CSS reverses the slider; `src/style.css` has no `input[type=range]` rule.)

Should: "slide **right** to lift faint features". The `rngMax` tooltip on line 64 is correct (`min(1, i/wl)`, smaller `wl` ⇒ brighter).

Evidence contradicting the author's claims: `WORKLOG.md` ("both sliders' hover text says which way brightens") and `README.md` ("both sliders say in their hover text which way brightens faint features") — one of the two is backwards.
