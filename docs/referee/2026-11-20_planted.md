## Findings

**1. [wrong result] The sign flip negates the sub-bin offset: manual "+ Ring" radii now land on the wrong side of the peak bin, by up to one profile bin**

Where: `/private/tmp/claude-501/-Users-cmserrao-Documents-GitHub/5c640452-3a19-4298-be36-60a3e6440aeb/scratchpad/planted/src/imageproc.js:859`

Input: any `+ Ring` click near a real ring. Concrete minimal case: a profile whose smoothed residual around bin `b` (radii 100, 101, 102 px, `workScale = 1`) is `rs = [10, 12, 11]`.

Happens: `den = 10 - 24 + 11 = -3`; new code `off = 0.5*(rs[i+1]-rs[i-1])/den = 0.5*(11-10)/(-3) = -0.167` → snapped radius `100.83`. The right neighbour is the *taller* one, so the true peak lies above 101, not below it. For `rs = [10, 12, 12]`: `den = -2`, new `off = -0.5` → `100.5`, whereas the peak is at `101.5` — a full bin of error, in the wrong direction.

Should: `off = 0.5*(rs[i-1]-rs[i+1])/den = +0.167` → `101.17` (and `101.5` in the second case). Fitting `p(x)=ax²+bx+c` through `(-1,y₋), (0,y₀), (1,y₊)` gives vertex `-b/2a = 0.5(y₋-y₊)/(y₋-2y₀+y₊)`, which is exactly the pre-change expression.

Evidence: the same file contains two independent copies of the correct convention that the change did not touch:
- `src/imageproc.js:681` (ring detection, the code `snapRing` is documented to reproduce): `const off = den < 0 ? 0.5 * (rs[b - 1] - rs[b + 1]) / den : 0;`
- `src/imageproc.js:354` (`para` helper used by centre finding): `0.5 * (m - p0) / d2` with `m` = minus side, `p0` = plus side.

The error in original pixels is `2·|off|·f`, where `f = workScale = max(1, ceil(max(W,H)/2048))` (`src/imageproc.js:284`) because profile rows are spaced `f` px apart (`src/imageproc.js:827`). On the four ~4096 px samples (`samples/README.md:5,10,13,14`) `f = 2`, so a manual ring can be placed up to 2 px off the peak the detector would have chosen.

**2. [wrong result] The same physical ring now gets two different d-spacings depending on whether it was auto-detected or hand-marked**

Where: `/private/tmp/claude-501/-Users-cmserrao-Documents-GitHub/5c640452-3a19-4298-be36-60a3e6440aeb/scratchpad/planted/src/imageproc.js:859` vs `:681`; consumed at `/private/tmp/claude-501/-Users-cmserrao-Documents-GitHub/5c640452-3a19-4298-be36-60a3e6440aeb/scratchpad/planted/src/app.js:754` and `:129`

Input: a user clicks "+ Ring" on a ring the detector already found (or on a ring in a 4096 px pattern, where `f = 2`).

Happens: detection stores `r = (b + off)·f` (`imageproc.js:682`, `:821`); `snapRing` now returns `(b − off)·f`. The two differ by `2·off·f`. `addRing` writes that straight into `feat.r` (`app.js:756`), and `recomputeD` turns it into `f.q = r·scale; f.d = 1/q` (`app.js:129`). The relative d error equals the relative r error, `2·|off|·f / r`. Using the radii the work log itself quotes for the Au standard (`WORKLOG.md:267`: halo at 212 px, ring at 1055 px, `f = 1`): up to 0.47 % at 212 px. On a 4096 px pattern (`f = 2`) an inner halo at r ≈ 100–200 px shifts by up to 2 px, i.e. 1–2 % in d — inside the 2 % tolerance of plan check 5 (`PROMPT.md:65`), so it looks plausible and will not be caught by the hand comparison either.

Should: a click on a ring reproduces the detector's radius, as the function's own docstring promises: "the residual is smoothed the way the ring detection smooths it, so a click on a ring lands where the detection would put it" (`src/imageproc.js:847-849`, unchanged by this commit).

**3. [wrong result] Near-equidistant peaks: the nearest-peak choice can now select the wrong ring**

Where: `/private/tmp/claude-501/-Users-cmserrao-Documents-GitHub/5c640452-3a19-4298-be36-60a3e6440aeb/scratchpad/planted/src/imageproc.js:860,865`

Input: two peaks within the snap window `win = max(8, 0.05·r0)` at bins 200 and 203 (`f = 1`) with true sub-bin offsets `+0.4` and `−0.4` (true radii 200.4 and 202.6), clicked at `r0 = 201.6`.

Happens: candidates are stored as `rr[i] + off·(rr[i+1]-rr[i])` with the negated `off`, i.e. 199.6 and 203.4; distances 2.0 and 1.8 → the outer ring wins. With the correct sign the candidates are 200.4 and 202.6; distances 1.2 and 1.0 → the outer ring also wins here, but swap the offsets (`−0.4`, `+0.4`, click at 201.6) and the selection reverses between the two versions. The tie-break at line 865 compares the *offset* radii, so a sign error of up to one bin in each candidate can change which feature is marked, not merely its sub-pixel position.

Should: the offsets used for nearest-peak ranking are the physical peak positions, so the ranking matches what the user sees.
